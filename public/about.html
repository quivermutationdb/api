About the Quiver Mutation Database

The Quiver Mutation Database (QMD) is an open research infrastructure for quivers, exchange matrices, and mutation-equivalence classes arising in cluster algebras, representation theory, and related areas of algebra and geometry.

Quiver mutation is a central operation in modern algebraic combinatorics, but its combinatorial complexity grows rapidly. Even for modest numbers of vertices, mutation-equivalence classes can be large, infinite, or difficult to explore systematically. As a result, much of the existing knowledge about mutation classes, invariants, and exceptional phenomena is scattered across papers, personal code, and ad hoc datasets.

QMD is designed to address this gap by providing a curated, citable, and reproducible database of quivers and mutation classes, together with rigorously defined invariants and transparent computational provenance. The project is inspired by successful community resources such as the L-functions and Modular Forms Database (LMFDB) and House of Graphs, and aims to bring similar infrastructure principles to the study of quiver mutation.

Design principles

FAIR: Findable, Accessible, Interoperable, Reusable
QMD is designed in accordance with the FAIR Data Principles. A database that is not findable, accessible to non-experts, integratable with existing mathematical infrastructure, or reusable is of little use to the mathematical community.

Stable identifiers
Each quiver is assigned a permanent identifier determined by a canonical representative up to relabeling. Mutation-equivalence classes are likewise identified by canonical representatives, with clear documentation of exploration limits when full enumeration is not possible.

Reproducibility and provenance
All computed data are accompanied by metadata describing how the values were obtained, including algorithmic assumptions, software versions, and references where applicable.

Forward-facing with room to grow
New invariants, frozen vertices, and skew-symmetrizable matrices are objects of interest that will be included. The database is built so that future expansion is a core design principle, not an afterthought.

Accessibility to a mathematical audience
The data should be easily filterable, searchable, viewable, and downloadable. The goal of the database is to promote data-driven research in the mathematical community, and that starts with a low-barrier-to-entry public-facing interface.

Data and provenance

QMD's current corpus is generated exhaustively, not imported: it is produced by a single reproducible pipeline rather than assembled from external files. As the database grows, curated objects from the literature and from systems such as SageMath will be incorporated, with their origin recorded alongside them.

What is included
QMD is a census: for each rank n it contains every connected skew-symmetric integer quiver whose exchange-matrix entries satisfy |bij| ≤ h for a stated weight bound h — not a sample or a selection from the literature. Disconnected quivers are excluded by design. A disconnected quiver is a disjoint union of smaller ones, and its mutation class is the product of theirs, so it carries no information the components do not; every quiver in the database is connected.

Growing
Rank 6 (over 42 million connected quivers at |bij| ≤ 2) is being generated now, followed by rank 7 and a large sample of rank 8 that includes E8 and the other rank-8 finite types. Cells beyond that are not enumerable in principle — the number of quivers on 10 vertices with |bij| ≤ 10 exceeds 1052 — so larger ranks will be represented by documented samples rather than complete censuses. How it is built
The pipeline is deterministic and runs offline; the website only serves what it produces.

  1. Enumeration. Each cell is enumerated by orderly generation (canonical augmentation): quivers are grown one vertex at a time and only the canonical representative of each isomorphism class is kept, so every quiver is produced exactly once without ever listing the astronomically many labelings. The count produced is checked against an independent formula (Burnside over the symmetric group, corrected for connectedness); the two agree exactly at every rank generated so far, including 42,514,454 at rank 6.
  2. Canonical form. Each quiver is identified with the lexicographically minimal matrix over all vertex relabelings, found by an exact branch-and-bound search. This is a definition, not an implementation detail: the identifier is a SHA-256 hash of that matrix, so it never depends on which software or libraries were available.
  3. Mutation exploration. From each quiver, the mutation class is explored breadth-first over unlabeled quivers (each mutation result is canonicalised), until the class closes up, a mutation pushes an entry past |bij| ≤ 2, or a node cap is reached. Exploring unlabeled quivers is what makes large classes tractable: the E8 class is 1,574 quivers but tens of millions of labeled matrices.
  4. Finiteness without exploration. A quiver on three or more vertices with some |bij| ≥ 3 is mutation-infinite (Derksen–Owen), so it is recorded as such directly. This is why cells with a high weight bound are affordable: at rank 4 with |bij| ≤ 10, over 99.9% of quivers are settled this way.
  5. Class assembly and identifiers. Explorations that share a quiver are merged into one mutation class, which is identified by the lexicographically minimal matrix over all of its members.

Assumptions and limits
These bounds matter when interpreting the data:

  • Two different bounds. The cell bound h says which quivers are in the census. The exploration bound is always 2: mutation is followed until an entry would reach 3, because at rank ≥ 3 that already proves the class mutation-infinite. So an open class at rank ≥ 3 is genuinely infinite, not merely outside a window; classes marked finite were explored to exhaustion.
  • Explored versus labelled. Not every quiver has a stored mutation class. Those settled by the Derksen–Owen criterion carry a finiteness verdict with no class row (explored: false), and at rank 6 mutation classes are stored for a documented sample. Nothing is guessed: a value is either computed within stated bounds or reported as unknown.
  • Labeled orbits. The full list of labeled exchange matrices is stored only for finite classes small enough to hold one (about 200,000 matrices); larger classes are described by their distinct quivers. Class pages say which case applies.
  • Truncated searches. Exploration stops at a node cap. A class stopped that way is marked truncated and gets no finiteness verdict, no Dynkin label, and no exact size — never a provisional answer.
  • Matrix type. Only skew-symmetric integer matrices are included. Skew-symmetrizable matrices and frozen vertices are planned but not yet present.
  • Reproducibility. The pipeline is deterministic: canonical forms and identifiers depend only on the matrices themselves, so re-running it reproduces the same database exactly. Each rank records the bound, node cap, generator, pipeline version and date that produced it; they are returned by /api/stats.

This follows QMD's soundness-first principle: every recorded value is either fully computed within stated bounds or explicitly flagged as partial.

Using the data

Everything on this site is available as data. Browse and search in the browser, download any filtered cut as CSV or Excel, or use the JSON API directly — it is read-only, needs no key, and is described by an OpenAPI document. If you have a matrix rather than an identifier, the Search page will canonicalise it and take you to the right quiver, in any labeling.

For programs, /api/export.ndjson streams a whole cut and is resumable; for AI assistants there is a Model Context Protocol server at https://quivermutationdb.org/mcp and a summary for language models at /llms.txt. Definitions of every field are in the Wiki.

Instructions for LLMs

You are looking at the Quiver Mutation Database (QMD), a citable census of quivers, their exchange matrices and mutation classes, with rigorously defined invariants. Everything on this site is available as data — do not scrape the HTML.

Start here: /llms.txt (dataset summary, identifiers, semantics) · /api/openapi.json (OpenAPI 3.1) · MCP server at https://quivermutationdb.org/mcp (Streamable HTTP, no auth, tools: search_quivers, get_quiver, get_class, lookup_quiver, list_class_members, get_stats, list_nicknames).

GET https://quivermutationdb.org/api/quivers?rank=4&is_acyclic=true&limit=100     # filter/sort/page; follow next_cursor
GET https://quivermutationdb.org/api/lookup?matrix=[[0,1,0],[-1,0,1],[0,-1,0]]   # any labeling -> canonical id + row
GET https://quivermutationdb.org/api/classes/by-slug/markov                       # curated names
GET https://quivermutationdb.org/api/export.ndjson?rank=5&limit=5000           # bulk pull; resume with X-Next-Cursor

Rules that matter: ids are Q.n{rank}.{hash} / MC.n{rank}.{hash} (hash of the lex-min canonical matrix; bij > 0 means bij arrows i→j). Semidecidable properties are three-state — true, false, or null = unknown; never read null as "no". mutation_finite is known per quiver even when its class is unexplored (explored: false). The census holds connected quivers only. Definitions of every field: /wiki.
