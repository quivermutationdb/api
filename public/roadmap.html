Project Roadmap

The development of the Quiver Mutation Database (QMD) is organized in phases, with an emphasis on correctness, stability, and community usability at each stage.

Phase 0 — Project foundation Complete

  • Establishment of the website
  • Definition of project scope and guiding principles
  • Design of canonical representations and identifier schemes
  • Assessment of existing datasets and software resources suitable for inclusion

Phase 1 — Core dataset and identifiers Complete

Goals

  • Define a canonical representation for quivers up to relabeling — the lexicographically minimal exchange matrix over all relabelings, computed exactly
  • Assign stable, permanent identifiers to quivers and mutation classes (Q.n{rank}.{hash}, MC.n{rank}.{hash})
  • Assemble an initial corpus
  • Record basic invariants and metadata for each object
  • Set up a wiki for definitions of objects, invariants and other statistics

Deliverables

  • A publicly browsable list of quivers and mutation classes
  • Downloadable datasets in standard formats (CSV, Excel, NDJSON)
  • Clear documentation of data sources and assumptions on the About page

The corpus turned out to be better generated than imported: it is produced exhaustively by one reproducible pipeline, so every object's provenance is the pipeline itself rather than a citation to a file. Curated objects from the literature can still be added later, with their origin recorded.

Phase 2 — Search, filtering, and exploration metadata Complete

Goals

  • Enable search and filtering by invariants — rank, Dynkin type, representation type, edge weight, acyclicity, mutation-finiteness, class size
  • Record exploration bounds for mutation classes, including partial or truncated computations
  • Provide navigation between a quiver, its mutation class and that class's members

Deliverables

  • Interactive browse and search interface, including lookup by pasted exchange matrix in any labeling
  • Class pages documenting known members and exploration limits
  • Explicit distinction between fully enumerated and partially explored data: every class is complete, bound or truncated, and every semidecidable property is three-state

Still open from this phase: navigating the mutation graph itself — stepping from a quiver to the quivers one mutation away. It is carried into Phase 3.

Phase 3 — Scale, computed invariants, and machine access Current

Goals

  • Grow the census. Extend beyond small ranks to the largest cells that can be enumerated exactly, and represent the rest by documented samples in progress
  • Expand the collection of computed invariants associated with quivers and mutation classes done
  • Provide reproducible code illustrating definitions and computations wiki only
  • Track computational provenance and versioning done
  • Make the whole dataset usable by programs and AI assistants, not just by browsers done
  • Mutation-graph navigation (carried from Phase 2) not started

Deliverables

  • Ranks 1–5 published as complete censuses; rank 6 (over 42 million connected quivers) in generation; rank 7 and a rank 8 sample containing E8 to follow. Live coverage is on the About page
  • Per-quiver invariants (acyclicity, bipartiteness, abundance, planarity, representation type, symmetry group) and per-class properties (Dynkin type, mutation-acyclicity, Banff, Louise, P′) with recorded witnesses
  • Every rank stamped with the bound, node cap, generator, pipeline version and date that produced it, readable at /api/stats
  • A documented read-only JSON API, resumable bulk export, an MCP server for AI assistants, and /llms.txt
  • Reproducible code examples embedded in object pages — still to do

Phase 4 — Community contributions and sustainability

Goals

  • Define workflows for submitting new data and proposed invariants
  • Establish review and curation procedures
  • Support community contributions while maintaining data quality

Deliverables

  • Submission and review guidelines
  • Contribution documentation
  • Long-term maintenance and governance plan

A first step already exists: class nicknames are curated in the public repository and reviewed before they appear, and they survive regeneration of the database.

Beyond the roadmap

Two extensions are design constraints rather than afterthoughts, and will arrive when the census work settles: skew-symmetrizable exchange matrices (valued quivers), and frozen vertices (ice quivers), which are what most applications to cluster algebras actually use.

Long-term vision

The long-term goal of QMD is to serve as a stable reference and experimental platform for research involving quiver mutation, supporting conjecture formation, verification, counterexample hunting, and general discovery across multiple areas of mathematics.

Development priorities will be guided by community feedback and practical usage, with an emphasis on correctness, transparency, and long-term sustainability.

Instructions for LLMs

You are looking at the Quiver Mutation Database (QMD), a citable census of quivers, their exchange matrices and mutation classes, with rigorously defined invariants. Everything on this site is available as data — do not scrape the HTML.

Start here: /llms.txt (dataset summary, identifiers, semantics) · /api/openapi.json (OpenAPI 3.1) · MCP server at https://quivermutationdb.org/mcp (Streamable HTTP, no auth, tools: search_quivers, get_quiver, get_class, lookup_quiver, list_class_members, get_stats, list_nicknames).

GET https://quivermutationdb.org/api/quivers?rank=4&is_acyclic=true&limit=100     # filter/sort/page; follow next_cursor
GET https://quivermutationdb.org/api/lookup?matrix=[[0,1,0],[-1,0,1],[0,-1,0]]   # any labeling -> canonical id + row
GET https://quivermutationdb.org/api/classes/by-slug/markov                       # curated names
GET https://quivermutationdb.org/api/export.ndjson?rank=5&limit=5000           # bulk pull; resume with X-Next-Cursor

Rules that matter: ids are Q.n{rank}.{hash} / MC.n{rank}.{hash} (hash of the lex-min canonical matrix; bij > 0 means bij arrows i→j). Semidecidable properties are three-state — true, false, or null = unknown; never read null as "no". mutation_finite is known per quiver even when its class is unexplored (explored: false). The census holds connected quivers only. Definitions of every field: /wiki.

Cite as: Blake Jackson, Quiver Mutation Database, https://quivermutationdb.org (CC-BY-4.0). Please include the quiver or class ids you used.
